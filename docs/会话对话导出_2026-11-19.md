### 助手
已克隆并查看仓库 `RAG_drift`（项目名 `intelligence-rag`），它是一个面向**无人机技术、故障与安全、产业供应链及学术文献**的可观测开源情报 RAG 与知识图谱原型系统。

以下从**整体架构**、**RAG 检索与问答**、**知识图谱构建**以及**评测与质量标准体系**四个方面梳理核心代码：

#### 一、整体架构与技术栈
- **后端 (`backend/app/`)**：FastAPI + SQLAlchemy (Async) + Alembic + Pydantic v2。
- **存储层**：
  - **PostgreSQL**：保存原始内容、切片（`ContentChunk`）、采集任务、会话历史及专题业务表（供应链、IEEE 文献）。
  - **Qdrant**：向量检索（默认 SiliconFlow BGE-M3）。
  - **Neo4j**：视频/文档知识图谱、构图任务与检查点。
- **异步与工具层**：
  - `worker/app/`：通用采集任务领取、内容规范化与切片索引。
  - `tools/`：包含论坛采集（`forum-crawler`）、YouTube 视频采集（`video-crawler`）、iFixit 维修指南（`ifixit_rag`）、供应链抽取（`supplier-information`）、文档/视频知识图谱工具等。
  - `frontend/`：React + TypeScript + Vite 控制台（包含检索、AI 问答、视频图谱、数据库浏览等视图）。

#### 二、RAG 检索与问答链路 (`backend/app/services/`)
1. **混合检索 (`retrieval.py`, `query_matching.py`, `reranking.py`)**
   - 结合 PostgreSQL 关键词匹配与 Qdrant 语义向量检索，保留完整型号短语，按查询覆盖度与向量相关性排序，并在截断前分散来源。
   - 支持可选的 Reranker（如 `SiliconFlowReranker`）。
2. **上下文组装与答案生成 (`answer_context.py`, `answer_generation.py`, `conversation_policy.py`)**
   - `LLMAnswerClient` 通过兼容 OpenAI Chat Completions 的接口生成回答，默认上下文预算 `12,000` 字符、最多 8 条证据。
   - System Prompt 强制“结论优先、按板卡/部件分组、保留原限定词（如 Likely/possibly）、句末标注 `[n]` 引用”，并明确要求图谱关系需结合引句核验。
3. **引用后验校验 (`citation_check.py`)**
   - `validate_citations()` 在生成后用正则解析 `[n]` 标记，输出 `CitationCheckResult`（包含 `cited_indices`、`out_of_range_indices`、`uncited_evidence_indices`、`marker_count`），记录到生成 trace 中（状态分为 `ok` / `no_citations` / `invalid_citations`）。

#### 三、知识图谱构建与检索 (`backend/app/services/video_graph/`, `document_graph/`, `knowledge_graph/`)
- **图谱抽取与校验**：从视频字幕/摘要或文档中抽取实体与关系（如 `LLMVideoExtractor`），配合 `validation.py`、`identity.py` 做实体身份哈希与规则校验，写入 Neo4j（`storage.py`）。
- **图谱检索 (`graph_retrieval.py`, `graph_evidence_text.py`)**：提供独立的图谱上下文检索接口 `retrieve_graph_context()`（`README.md` 说明目前 `/answer` 尚未自动融合图谱结果，图谱走独立检索接口）。

#### 四、评测脚本与质量标准 (`scripts/` 与 `scripts/evaluation_data/`)
1. **实体与关系抽取 Gold 评测**
   - `evaluate_entity_gold.py` / `evaluate_relation_gold.py`：不写图谱库，直接用标注集（`entity_gold_v1/v3.json`、`relation_gold_v1/v3.json` 及对应 guidelines）评估抽取器，支持响应缓存（`video_graph_response_cache.py`）和一对一实体匹配规则。
   - `evaluate_document_graph_gold.py`：对应多模态文档图谱评测集 `document_multimodal_gold_v1.json`。
2. **图谱发布门禁标准 (`video_graph_release_criteria.json` & `evaluate_video_graph_quality.py`)**
   - 目标保留率下限：`target_retention_min: 0.8`
   - 已知坏例拒绝率下限：`known_bad_rejection_min: 0.9`
   - 抽样人工复核（60 条固定种子样本）：至少 51 条 `supported`、最多 3 条 `issue`、最多 6 条 `review`。
3. **检索 Reranker 与证据数量对比实验**
   - `evaluate_answer_evidence_counts.py` 与 `evaluate_reranker.py`：在冻结的 60 候选池上测试不同 `(候选数, Top-K)` 组合（`baseline8`、`c20_k8`、`c40_k4/k8/k12/k20`、`c60_k8`）对回答质量与延迟的影响，并生成带 SHA256 校验的 `manifest.json` 保证实验可复现。

- **科学问题**：
  > **在口语化、含噪且存在推测性表述的非结构化文本中，如何将“不确定性、否定与前提条件”显式建模进知识图谱抽取与评测标准中，并量化其对下游 RAG 回答忠实度（Faithfulness）与幻觉抑制的贡献？**

#### 思路 2：强型号约束下的“向量-图谱协同检索”与语义级引用可验证性
- **项目观察**：`RAG_drift` 的 `/search` 与 Neo4j 图谱检索目前是分离的；且历史验收曾出现“型号关键词压过部件语义”的排序问题。此外，`citation_check.py` 目前只做 `[n]` 编号是否越界的形式校验，无法判断证据是否真正支持该句论断。
- **科学问题**：
  > **面向“强实体型号约束 + 跨源多跳推理”的专业领域问答，如何设计向量切片与知识子图的动态融合检索机制，并构建超越“编号合法性”的细粒度引用可验证性（Citation Grounding）评估与约束方法？**
- **可对接论文**：`GraphRAG`、`LightRAG`、`ALCE`。

#### 思路 3：固定上下文预算下的“证据数量-重排”拐点与检索漂移（Context Drift）诊断

- **科学问题**：
  > **在有限上下文窗口与噪声候选共存的 RAG 系统中，检索 Top-K 扩张与重排（Reranking）在何种条件下会从“信息增益”转变为“上下文干扰（Context Drift）”？如何通过去偏的模块化诊断指标解耦检索失效与生成失效？**
- **可对接论文**：`RAGAS`、`ARES`（PPI 校准）、`RAGChecker`。

#### 思路 4：持续增量多源情报流中的“实体分裂与关系漂移”控制
- **项目观察**：`RAG_drift` 通过定时任务持续增量采集论坛新回复、YouTube 新视频、供应链网页与手册，极易产生别名分裂或关系类型膨胀。

- **可对接论文**：`LightRAG`、`KGGen`。

### 用户

### 助手
以下是对论文 **[llm知识图谱抽取.pdf](file:///c:/Users/gaowei/Desktop/RAG与图谱性能标准/llm知识图谱抽取.pdf)**（*KGGen: Extracting Knowledge Graphs from Plain Text with Language Models*，NeurIPS 2025，Stanford / U of T / FAR AI）的逐节细读与批判性分析。

#### 一、 核心问题与动机：为什么现有文本抽图不好用？
1. **OpenIE（基于依存句法与规则/分类器）**：抽出的节点往往是冗长碎片或无意义代词/系动词（如 `"it"`、`"are"`），导致无关概念通过 `"it"` 两跳相连，图结构失真且同义节点大量重复。
2. **Microsoft GraphRAG**：虽然下游问答效果不错，但抽出的图**极度稀疏、关系无法复用**——在长文本上边类型数几乎等于边数（例如 100 万字符小说中 981 条边对应 966 种边类型），且边标签往往是一整段描述性长句（Figure 4），无法用于 TransE/TransR 等传统图嵌入或规范化图谱推理。

**KGGen 的核心目标**：从纯文本中抽取出**高密度、低冗余、关系类型可复用、符合 `(subject, predicate, object)` 规范**的知识图谱，同时提出首个直接衡量纯文本抽图质量的基准 **MINE**。

#### 二、 KGGen 方法论拆解（3 阶段流水线）
1. **阶段一：两步式 LLM 抽取（Section 4.1 & Appendix A）**
   - 使用 **DSPy Signatures** 约束结构化输出：Step 1 抽实体列表；Step 2 将原文 + 实体列表输入，强制 `(subject, predicate, object)` 的头尾实体来自实体列表，保证局部实体一致性。
2. **阶段二：跨文本聚合（Aggregation, Section 4.2）**
   - 收集所有文本块抽取出的实体与边，**全部转为小写**并做精确字符串去重，合并为一张初始大图（不调用 LLM）。
3. **阶段三：基于“聚类 + 混合检索 + LLM”的迭代实体/边消歧（Section 4.3 & Figure 1）**
   - 对实体集和边集分别执行：
     1. 用 `S-BERT` 嵌入并通过 k-means 聚成每组约 **128 个元素**的簇；
     2. 簇内使用 **BM25 + 语义嵌入融合检索** 取 Top-`k=16` 候选；
     3. 让 LLM 识别**真正语义等价的重复项**（时态、单复数、词干、大小写、缩写/简写变体）并选出 canonical alias；
     4. 从簇中移除已归并项并迭代直到清空（Figure 1 显示还会对未聚类节点再跑 `m times` 批次消歧）。
   - Prompt 强约束防止把相似但不同的概念合并（如 `Type 1` vs `Type 2 diabetes`、`MRI` vs `CT scan`）。

#### 三、 MINE 评测基准设计（Section 5 & Appendix B）
- **MINE-1（知识保留度）**：100 篇 LLM 生成短文（平均 592 词），每篇配 15 条经人工核验的原子事实；用 `all-MiniLM-L6-v2` 检索 Top-`k` 节点并扩展**两跳邻居**，**仅把检索到的子图**喂给 LLM 裁判判断能否推导出事实（`1`/`0`；60 样本人工核验一致率 90.2%，相关性 0.80）。
- **MINE-2（下游 Graph-RAG）**：WikiQA（1,995 篇文章，20,400 个问题）；50% BM25 + 50% `all-MiniLM-L6-v2` 检 Top-10 三元组 + 10 条两跳扩展三元组 + **关联原文切片**输入生成器，LLM-as-a-Judge 判 `Yes/No`。

#### 四、 核心实验结果（Section 6）
