# iFixit 无人机维修数据 RAG 处理方案

日期：2026-10-21。状态：设计方案，尚未实施数据转换或入库。

本方案依据本轮对话对 `data/ifixit数据/` 的本地检查，以及仓库现有内容模型、分块、索引和检索代码制定。目标是将维修指南转换成可追溯、保留操作顺序、支持中文提问的 RAG 数据。采用“指南作为上下文、步骤作为主要检索单元”的方式，先完成文本检索与来源引用，再扩展图片理解和视频转录。

**1. 数据基线与处理边界**

| 项目 | 本地检查结果 | 处理含义 |
|---|---:|---|
| 指南 | 391 篇，391 个不同 guideid | 一篇指南对应一个规范化文档 |
| 设备分类 | 89 个原始 category | 包含无人机、遥控器等，不直接等同于无人机型号数 |
| 语言 | 全部为英文 | 保留原文，验证中文查询召回 |
| 指南类型 | replacement 334、technique 34、disassembly 14、teardown 9 | 保留类型，支持按任务筛选 |
| 步骤与文字条目 | 2,028 步、3,902 条文字 | 以原有结构生成步骤记录 |
| 空步骤指南 | 79 篇，其中 68 篇简介含视频标记或链接 | 不按空文档直接丢弃 |
| 本地图片 | 4,092 张，JPEG 头部与尺寸可读取，均为 300×225 | 尚不代表完成全图解码验证；细节识别能力有限 |
| 图片内容去重 | 2,532 个 SHA-256，1,560 份重复副本 | 可共享资产，保留各处引用关系 |
| 有工具／零件／前置指南字段内容 | 294／85／122 篇 | 空列表表示未提供，不能解释为无需工具或零件 |
| 缺失的前置 guideid | 35944、114408、126918、159327、181254 | 建立未解析引用，后续按需补采 |
| 数据体积 | 约 59 MiB | 首版适合一次全量处理，随后按哈希增量更新 |

391 份 Markdown 中的 JSON 均能解析。原始数据仅作为输入，派生数据写入新目录。源站发布时间、修改时间与本地导入时间分开记录；文件修改时间不能用作抓取时间。方案不假设本地内容等同于源站最新内容。

以下 5 篇的“封面图片引用数＋步骤图片引用数”与本地图片数不一致：

| guideid | 指南 | 引用数 | 本地图片数 |
|---|---|---:|---:|
| 105217 | Protocol Kaptur GPS Motor Replacement | 24 | 23 |
| 131316 | 3DR Iris Plus Quadcopter RX Transmitter Replacement | 27 | 26 |
| 201946 | DJI Phantom 3 Standard Propeller Motors Replacement | 24 | 23 |
| 35950 | DJI Phantom Motor Replacement | 39 | 6 |

这只是数量异常，不能直接据此判定缺失了哪张图；引用可能重复，下载流程也可能去重。优先核对 35950，并逐篇建立有依据的媒体映射。

**2. 处理流程与阶段产物**

```text
原始 Markdown / JSON / 图片
  → 输入清单与哈希
  → JSON 解析、字段校验、正文清洗
  → 规范化指南、步骤、媒体引用和前置依赖
  → 质量检查与异常分流
  → 指南概览块、步骤块、简介块
  → PostgreSQL 内容存储与关键词检索 + Qdrant 向量索引
  → 检索、相邻步骤补全、证据引用与效果评估
```

建议输出到 `data/processed/ifixit/<run_id>/`，每次运行保留独立清单和版本：

| 文件 | 记录粒度与用途 |
|---|---|
| `manifest.json` | 输入文件哈希、运行时间、配置、各阶段版本、输出数量与哈希 |
| `guides.jsonl` | 一篇一条，包含指南正文、设备、工具、零件和来源 |
| `steps.jsonl` | 一次步骤出现一条，保留所属指南、原始 stepid、原始 guideid、顺序及文字条目 |
| `assets.jsonl` | 一个唯一文件哈希一条，记录路径、类型、尺寸和解码状态 |
| `media_refs.jsonl` | 一次封面或步骤媒体引用一条，关联远端图片标识与本地资产 |
| `relations.jsonl` | 指南前置依赖等关系，记录目标是否存在、是否已经包含在步骤中 |
| `chunks.jsonl` | 一个检索块一条，含正文、向量化文本、定位和元数据 |
| `quality_report.json` | 全局统计、逐指南异常、分流结果和待修复项目 |
| `evaluation.jsonl` | 人工核验的问题、预期证据、设备约束与可回答性 |

以上为拟新增产物。JSONL 均使用 UTF-8，路径采用项目相对路径，空值与空列表保持明确语义。

**3. 解析与正文清洗**

1. 识别 Markdown 中的 JSON 代码块，解析后校验必要字段、类型、目录 ID 与 guideid。解析失败的文件写入错误清单，不能静默跳过。
2. 保留完整原始 JSON 和文件哈希。主要正文来自 `introduction_raw`、`steps[].lines[].text_raw`、`conclusion_raw`；对应 rendered 字段作为辅助，不重复拼入正文。
3. 将 iFixit 标记转换为可读文字。例如 `[product|IF145-020|tweezers]` 转成 `tweezers`，产品 ID 另存；普通链接保留标签和地址；视频标记转成媒体引用。未知标记记录清洗告警，避免用宽泛正则误删内容。
4. 清理 HTML 标签、实体、重复空白及无意义格式，同时保留段落、列表、命令、数值、单位、螺丝数量、旋转方向和否定表达。代码或命令中的空格不能按普通段落随意折叠。
5. 每条操作保留 `bullet` 和 `level`。已知的 warning、note、reminder 标记转换成语义标签；颜色标记保留，用于与图中颜色对应。未知值保留原值。
6. 作者、评论、重复图片尺寸 URL 等不进入默认检索正文，但原始快照中保留。源站 summary 可能截断，不能替代完整简介或步骤。

清洗只改变表示形式。疑似有误的尺寸、过时说明等保留原文并标记，不自动修正维修事实。许可证或署名信息若原始数据未提供，标记未知，发布数据集前再核实。

**4. 规范化数据模型与身份**

| 对象 | 必备字段 |
|---|---|
| 指南 | `document_id`、`guide_id`、`locale`、`title`、`category_raw`、`device_key`、`subject_raw`、`guide_type`、`introduction`、`conclusion`、`tools`、`parts`、`difficulty`、`time_required_min/max`、`source_url`、`source_path`、`source_revision`、`content_hash`、`quality_flags` |
| 步骤 | `step_occurrence_id`、`document_id`、`source_step_id`、`source_guide_id`、`source_revision`、`step_order`、`title`、`lines`、`media_ref_ids`、`text_hash` |
| 媒体引用 | `media_ref_id`、`document_id`、`step_occurrence_id`、`role`、`media_order`、`source_media_id`、`source_guid`、`source_url`、`asset_sha256`、`mapping_status`、`mapping_evidence` |
| 检索块 | `logical_chunk_key`、`document_id`、`chunk_index`、`chunk_type`、`step_occurrence_ids`、`display_text`、`embed_text`、`char_start/end`、`token_count`、`metadata`、`chunk_hash` |

指南身份采用 `ifixit:<guideid>:<locale>`。步骤出现身份包含宿主指南和原始 stepid；同一指南内若重复出现同一个 stepid，再增加出现序号。缺少 stepid 时使用有标记的顺序回退 ID，并报告质量异常。`step_order` 决定展示顺序，不能按 stepid 的大小排序。

某指南的步骤可能来自前置指南，因此同时保留宿主指南和步骤自身的 guideid。共享步骤可以用于去重，但不能丢掉它在不同维修任务中的位置和设备约束。

型号规范化先做空白清理、大小写比较键和人工确认的别名映射；原始名称始终保留。不能因为名称相似就合并 Mini 2 与 Mini 2 SE、Phantom 3 的不同版本，或无人机与对应遥控器。别名表需要版本号和依据。

**5. 图片、视频与前置指南处理**

图片处理先扫描文件，计算 SHA-256、读取尺寸并尝试完整解码。文件层按哈希共享存储，引用层保留一对多关系。只进行缩略图展示时仍需明确显示其实际尺寸。

`image_001.jpg` 等文件名没有内嵌远端标识，不能直接解释为“第一步第一张图”。优先查找下载日志或采集脚本中的映射规则；通过已知样本验证封面、步骤和去重顺序。无法证实时将 `mapping_status` 设为 `unresolved`，保留远端引用和本地候选文件，暂不向用户展示猜测的步骤配图。后续补采时直接生成 URL、源图片 ID、下载文件和哈希的映射表。

空步骤指南分流为以下类型：

- `intro_only`：简介本身有有效信息，生成简介块，明确没有结构化操作步骤。
- `video_reference`：保留视频链接及简介中的已知信息，不能据链接生成视频操作内容。
- `insufficient_content`：缺乏可回答正文，只保存目录和质量记录，不生成空向量块。

上述类型可与 `has_video_reference` 等标记组合使用。79 篇都进入规范化层，但不保证全部进入可回答的检索语料。视频扩展阶段获得字幕或转录后，独立记录来源视频、语言、时间戳、转录方式和版本，再与指南建立关联。

前置指南保留有向关系。用 stepid、来源 guideid 和正文核对前置步骤是否已包含在宿主指南中；已包含的内容不重复追加。缺失前置文档标记 `unresolved`，关系遍历设深度和循环检测，防止错误关联导致无限展开。

**6. 分块与上下文补全**

| 块类型 | 内容 | 适用问题 |
|---|---|---|
| `guide_overview` | 标题、设备、维修对象、简介、工具、零件、难度、耗时、前置条件 | “更换 GPS 需要什么工具？” |
| `repair_step` | 一个步骤及其全部文字条目、注意事项、图片引用 | “GPS 模块怎么取下来？” |
| `repair_step_group` | 同一指南内相邻的短步骤，保留各自序号 | “拆开外壳的操作顺序是什么？” |
| `guide_intro` | 空步骤指南中的有效简介 | “这个指南介绍哪种云台校准方式？” |

基础策略为一篇一个或多个概览块、一个完整步骤一个步骤块。先建立原子步骤，再按评估决定是否合并短步骤；默认不同时索引大量重叠组合。普通块可先以 150–400 token 为调参起点，最终硬上限由实际嵌入模型 tokenizer 与最大输入长度决定，计算时包含上下文前缀。

长步骤只能沿完整文字条目或句子边界拆分，保留 continuation 标记；警告与其约束的操作共同出现。标题、工具列表过长时拆成有类型的概览子块。不得静默截断正文。

`display_text` 用于呈现证据；`embed_text` 增加设备、指南标题、维修对象和步骤序号前缀。正文中出现的“它”“该部件”保留原句，通过前缀和相邻步骤补全上下文，不用模型改写成未经验证的部件名称。

先生成确定性的 `cleaned_text`，再计算正文块的字符区间。前缀不计入正文偏移；多个不连续字段组成的概览块采用字段引用定位，入库时字符偏移设为 null，并标记 `offset_basis=field_refs`。

对于“如何更换某部件”这类完整流程问题，命中步骤后应扩展到所属指南的必要步骤、概览和前置条件；针对单步问题则补充前后各一步作为初始策略。扩展受上下文预算限制，内容不全时明确标出缺失范围。

**7. 去重、增量处理与质量分流**

去重区分三个层次：同一指南同一语言按 document_id 更新；正文相同的步骤计算共享 text_hash，但保留设备和指南归属；图片按文件哈希去重。不同型号的相同文字不能直接折叠成同一条维修证据。

派生内容哈希纳入影响回答的正文、元数据、依赖及媒体关联。每次处理记录 `parser_version`、`normalizer_version`、`alias_version`、`chunker_version` 和嵌入模型标识。只有派生文本及模型配置均未变时才能复用向量；媒体关联变化也要同步元数据。

质量标记至少包含 `no_steps`、`video_reference_only`、`missing_introduction`、`image_count_mismatch`、`image_mapping_unresolved`、`image_decode_failed`、`missing_prerequisite`、`unknown_markup`、`invalid_step_order`。标记控制可用能力：缺图不阻止文本检索，缺正文阻止正文嵌入，前置缺失则在完整流程回答中提示证据缺口。

保存单条失败原因与重试状态。重跑不能生成重复指南或向量点；源文件从某次输入清单消失时先报告差异，不能自动当作源站删除。确认撤回的指南再停用内容及对应向量。

**8. 与当前项目对接**

仓库代码已有可复用的内容模型与检索链路：

| 位置 | 已有能力 | 本方案所需调整 |
|---|---|---|
| [content.py](../backend/app/models/content.py) | `ContentItem`、`ContentChunk`、JSON 元数据与索引状态 | 一篇指南一个内容项，建议 `item_type=repair_guide`；iFixit 专有结构放入元数据或关联产物 |
| [chunking.py](../backend/app/services/chunking.py) | `BuiltChunk`、展示与嵌入文本分离、默认按字符切块 | 增加读取结构化步骤的专用分块入口；现有默认 1200 字符逻辑不能直接保留维修步骤边界 |
| [chunk_indexer.py](../worker/app/chunk_indexer.py) | 切片同步、向量写入、失败状态与旧点删除 | 根据内容类型调用专用分块器；补充步骤、设备、质量和版本元数据的同步 |
| [retrieval.py](../backend/app/services/retrieval.py) | SQL 关键词与向量混合检索 | 扩展设备约束、相邻步骤回查、指南级聚合和证据输出 |
| [embeddings.py](../backend/app/services/embeddings.py) | 多种嵌入服务实现 | 用实际运行配置验证中英检索与输入长度，不将代码默认值视为当前部署配置 |

正式导入需创建或复用 SourceSite、CrawlRun、RawPage，因为 ContentItem 对三者的引用为必填。RawPage 保存输入 JSON 及导入来源；guideid 和 locale 组成 dedup_key；源站发布时间映射 published_at，源站修改时间另存元数据。

JSONL 中的逻辑块键与数据库 UUID 分开。索引器需保证逻辑键到持久化块 ID 的一致映射，并处理步骤重排或分块版本变化时的旧块、旧向量清理。不能直接绕过现有同步流程后又让通用索引器覆盖专用分块结果。

设备筛选不能仅把字段写入 JSON：需要同时对接搜索请求 schema、SQL 条件、Qdrant payload 与过滤器、结果响应。首版可复用已有 tags 保存规范设备键；新增独立字段时必须完成两路检索的一致性验证。

现有 Neo4j 模块服务于视频图谱。iFixit 的指南、步骤和前置关系首先保存在规范化产物及内容元数据中；若以后需要跨指南图遍历，再设计独立节点类型、关系和证据模型。

**9. 中文检索与回答约束**

保留英文原文，先用术语表扩展中文查询，例如“云台／gimbal”“电子调速器／ESC”“螺旋桨／propeller”。设备型号、部件编号和工具规格作为强匹配信号，型号不明确时避免默认匹配近似型号。

使用项目现有关键词与向量混合检索，分别记录两路召回情况。通过中文、英文同义问题对比评估跨语言效果；效果不足时再选择查询翻译、经核验的双语字段或适合的嵌入配置。模型生成的翻译或摘要保留生成版本和原文引用，不覆盖原始维修证据。更换嵌入模型时使用独立 collection 并重建索引，不能混用不同模型的向量空间。

结果聚合按设备和指南组织，共享拆卸步骤不能占满结果列表。回答引用至少包含指南 URL、guideid 和步骤编号；图片仅引用映射已确认的媒体。视频只有链接时，只回答简介已提供的信息。证据未包含某项尺寸、扭矩或操作时不补造数值。

**10. 实施顺序与验收**

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| A：离线规范化 | 解析、清洗、字段整理、图片清单、质量报告、规范化 JSONL | 所有输入均被计数；成功和异常记录可追溯 |
| B：检索语料 | 专用分块、逻辑块键、上下文关系、媒体映射状态 | 每块可回到原始字段或步骤；模型输入不会静默截断 |
| C：项目接入 | PostgreSQL 入库、专用索引流程、混合检索和来源展示 | 同输入重跑无重复；失败可重试；旧向量可对账 |
| D：效果评估 | 中英文问答集、错误分析、分块和查询调参 | 达到预先约定的检索及证据指标 |
| E：按需增强 | 高清图片补采、视频转录、图片辅助检索、图关系扩展 | 每项增强独立验证，保留可复现版本 |

固定当前输入快照时，数据层验收应满足：391 篇指南进入规范化层，2,028 个步骤出现和 3,902 条文字均有来源映射；79 篇空步骤指南全部有分流结果；4,092 个图片文件均有资产清单记录；已发现的数量异常与缺失依赖逐项出现在报告中。预期计数不是写死的生产规则，输入变化后重新统计。

测试重点包括：iFixit 标记转换、数值与警告保留、重复 stepid 和前置步骤处理、未确认图片映射不被发布、长步骤分块、中文型号检索、幂等导入、向量失败恢复和版本更新后的旧点清理。人工抽查至少 30 篇，覆盖不同品牌、长短指南、视频型指南及全部已知图片数量异常。

建立至少 60 个经人工确认的评估问题，覆盖工具、单步、完整流程、前置依赖、近似型号和无答案情况，同时包含中英文同义问题。每题记录 gold guideid、必要步骤、预期设备和可回答性；调参集与保留评估集按指南及共享步骤关系分组，避免同一证据的改写问题泄漏。

建议首轮目标为可回答问题 Guide Recall@5 ≥ 90%、步骤问题 Step Recall@10 ≥ 85%；多步骤问题按 gold 步骤集合计算召回率。另行报告错误型号率、引用准确率、无答案误答率和完整流程关键步骤覆盖率。设备错误、数值失真或不受证据支持的操作建议均进入人工阻断清单，不以平均召回率掩盖。以上为拟定验收目标，尚无实测结果。
