# ArduPilot / PX4 论坛采集调研与建议

调研日期：2026-10-21。实测时间：北京时间约 16:35–16:38。

本次仅低频读取公开接口、检查现有代码，没有修改采集实现、调度配置或业务数据库。

## 结论

- 两站均为 Discourse，首选公开 JSON API。此次匿名访问已验证主帖、回复、帖子流分页和长主题补齐接口。
- 使用“按主题完整归档 + 历史分批回填 + 常态增量 + 定期校验”。不建议通过浏览器滚动采集，也不建议只采集一次后停止更新。
- 增量发现使用公开帖子流，不能继续依赖轮换关键词的第一页搜索结果。
- 将“保存相关主题的完整上下文”和“进入 RAG 检索索引”分开，分类、语义相关性、技术价值分别判断。

## 1. 适合的接口与实测结果

| 接口 | 用途 | 实测 |
| --- | --- | --- |
| `/about.json` | 站点近期活跃统计 | 两站均 HTTP 200 |
| `/site.json` | 分类及父子关系 | ArduPilot 返回 127 个分类，PX4 返回 36 个 |
| `/categories.json` | 顶层分类及子分类标识 | 两站均 HTTP 200；不能把返回的顶层分类当成完整分类树 |
| `/posts.json` | 新公开帖子流，含主帖和回复 | 两站均 HTTP 200 |
| `/posts.json?before=<post_id>` | 按帖子 ID 向历史分页 | 两站均返回 50 条，所有返回 ID 均小于指定游标 |
| `/t/<topic_id>.json?include_raw=true` | 主题元数据、帖子 ID 流和首批正文 | 两站均 HTTP 200，样例返回 Markdown 原文 |
| `/t/<topic_id>/posts.json?post_ids[]=...&include_raw=true` | 批量补齐主题中的指定帖子 | 两站均 HTTP 200，样例缺失正文全部补齐 |

长主题实测：

- ArduPilot [主题 141753](https://discuss.ardupilot.org/t/141753)：`post_stream.stream` 有 22 个 ID，首批正文只有 20 条；批量补齐剩余 2 条，均包含 `raw`。
- PX4 [主题 49575](https://discuss.px4.io/t/49575)：帖子 ID 流有 23 个 ID，首批正文只有 20 条；批量补齐剩余 3 条，均包含 `raw`。

因此不能把一次主题响应的 `post_stream.posts` 当作全部回复。应以当前匿名身份可见的 `post_stream.stream` 为清单，分批获取正文并记录缺失 ID。批量大小建议从 20 条开始，根据站点限制调整。

保留 `topic_id`、`post_id`、`post_number`、`reply_to_post_number`、作者、时间、版本、已采纳答案标记及附件链接。`reply_to_post_number` 为空的主题内回复仍需保留。回复数统计不能代替 ID 清单：实测 ArduPilot 样例有 22 条帖子，但 `reply_count` 为 20。

首选 JSON API 的原因是正文和关联字段直接可用，无须模拟滚动、依赖 DOM 或运行浏览器。浏览器仅适合作为页面排查工具或接口缺失时的有限补充，不能用于绕过访问限制。若未来与站方合作，可考虑授权 API 或 webhook。

此次读取的两站 `robots.txt` 均对通用爬虫列出 `Disallow: /search`；新方案应使用公开列表和主题接口，避免继续依赖搜索路径。公开接口可访问不等于站方承诺无限批量访问。限速应按站点实际响应调整，而不是套用 Discourse 默认限额。

## 2. 活跃度与历史回填策略

以下直接来自本次读取的两站 `/about.json`，而非搜索引擎缓存。`Posts` 是站点帖子统计口径，包含主帖和回复等；站点总数不等于匿名身份实际可归档数量。

| 指标 | ArduPilot | PX4 |
| --- | ---: | ---: |
| 历史主题数 | 59,149 | 18,213 |
| 历史帖子数 | 562,368 | 98,656 |
| 近 30 天新主题 | 135 | 48 |
| 近 30 天帖子 | 1,250 | 425 |
| 近 7 天新主题 | 33 | 15 |
| 近 7 天帖子 | 289 | 101 |
| 近 24 小时新主题 | 10 | 2 |
| 近 24 小时帖子 | 77 | 12 |

近 30 天折算每天约 42 / 14 条帖子。日波动明显，不能把一次快照当成长期固定吞吐率；上线后应持续记录公开帖子流的实际增量。

建议：

1. 初次回填优先处理近期 12–24 个月相关技术主题、已采纳答案和重要版本讨论，再向历史扩展。时间范围是实施起点，不是丢弃旧知识的硬阈值。
2. 先枚举全站公开主题元数据，再按分类与语义筛选，相关主题抓全主帖和回复。历史枚举可使用分类主题列表，按固定创建顺序分页，结合 sitemap 或重复扫描核对，避免按活跃排序分页时页面移动导致漏项。全站帖子流也可用于历史核对，但不应为筛选少量主题反复下载整个站点所有正文。
3. 日常默认两站每 2 小时检查一次公开帖子流。若需要更低延迟，再将 ArduPilot 调整到每小时一次；当前量级不需要分钟级轮询。
4. 每日复核近期活跃主题；历史已归档主题以受控预算轮转复核，例如每月完成一轮。旧帖编辑、删除、重新公开不一定出现在新帖子流中，必须明确这类变更的检测延迟。
5. 历史回填和常态增量使用独立进度、共享站点限速。回填期间增量照常运行，避免历史任务形成新的采集空窗。

不建议无差别全量向量化。原始归档和向量索引的规模应分别预算。

## 3. 增量与可靠性设计

### 发现与完成状态分开

- 每个规范化站点保存独立的已提交发现游标 `last_discovered_post_id`。
- 每轮从 `/posts.json` 头部向历史翻页，直到覆盖上次游标，并保留一定重叠。
- 所有新帖子对应的主题任务持久化后，才提交发现游标。队列和游标的提交应具有事务一致性；抓取失败的主题留在重试队列中。
- 发现游标前进仅表示新内容已进入处理队列，不代表正文、过滤、切片或向量化全部完成。分别监控队列积压、最老任务年龄和成功同步时间。
- ID 可以不连续，不能逐个猜测 ID，也不能仅处理第一页。旧主题新增回复与新主题使用同一个发现机制。

### 幂等和编辑

- 内容身份使用规范化站点与 `post_id` 的唯一组合，主题身份使用站点与 `topic_id`。
- 内容哈希只表达正文变化；查询词、抓取时间、点赞数、浏览量等不得参与正文版本判断。
- 对相同 ID 执行幂等更新；原始快照可保留多个版本，检索默认使用当前有效版本。
- 周期复核主题时，除补齐新 ID，也要检查已保存帖子正文或版本变化。仅比较 ID 集合不能发现编辑。
- 对删除、不可见内容，需区分真实可见性变化与暂时请求失败。经确认后停止检索对应旧向量，保留内部同步状态。
- 没有站方事件流时，目标应是可恢复、可核对的最终一致；不能承诺捕获删除前短暂可见或从未公开的内容。

### 调度与请求失败

- 每站初始并发 1，请求间隔可从 1–2 秒开始；这是保守起点，不是已验证的站点配额。
- 超时、429、暂时性 5xx 使用有上限的指数退避和随机抖动；429 遵循 `Retry-After`。403、404、410 单独分类，避免无差别重试。
- 每个主题独立提交，两个论坛独立隔离；一个论坛失败不应阻止另一个论坛。
- 任务锁、数据库连接预检、超时、运行状态收尾、错误退出码和持久化重试队列共同保证可恢复。Docker 可统一环境，但不能替代这些机制。
- 正文归档、质量判断、向量化分别记录状态，模型或向量服务故障不应丢失已抓取内容。

建议验收：同一主题重复运行不增生副本；新增回复即使出现在旧主题也能补入；中途失败后恢复不跳过失败任务；编辑能更新当前索引；长主题正文覆盖当前公开可见 ID 清单。过滤率与采集完整率应分别统计。

## 4. 面向 RAG 的过滤

### 分类先分流，语义再判断

| 处理 | ArduPilot | PX4 |
| --- | --- | --- |
| 优先技术分类及其子分类 | ArduCopter、ArduPlane、Ground Control Software、Hardware、Companion Computers、Lua Scripting、Development Team | PX4 Autopilot、Flight Testing & Log Analysis、Pixhawk、MAVLink、MAVSDK、QGroundControl、ROS、Guides |
| 默认不进入无人机技术索引 | For Sale（120）、Wanted - Jobs（119）、明显闲聊和纯营销 | 招聘/求职（28、29）、Random（43）、纯站务 |
| 需语义判断 | General、Blog、Hardware Vendors、Archive、会议内容 | Uncategorized、Spotlight、Community、Coordination Calls |

分类 ID 仅为此次快照，实际规则应按各站完整分类树维护，并展开子分类。ArduPilot 的 Rover/Sub 等内容可标为“通用无人系统技术”，按目标 RAG 范围决定，不能把所有可迁移的控制、导航知识当成无关内容。

不能直接丢弃整个 General 或 Uncategorized。此次 ArduPilot 的 General 中有 `Dual gps hardware`；PX4 的 Uncategorized 中有 [Aruco marker detection and landing process](https://discuss.px4.io/t/aruco-marker-detection-and-landing-process/49501)。反过来，技术大类中也可能出现库存询价、招聘或推广帖。

### 主题与回复分别评价

- 先根据标题、分类、标签、主帖判断领域相关性；疑似相关但信息不足的主题进入待判定区，不立即丢弃。
- 对相关主题保存完整公开上下文，再按问题、诊断依据、代码、参数、复现步骤、技术解释、验证结果等抽取可检索证据。
- 明确的广告、招聘、买卖、纯闲聊可用规则排除；边界案例交给模型，输出相关性、技术价值、内容角色、原因和分类器版本。
- 不要求必须出现 `drone` 或 `UAV`。例如 EKF 参数、I²C 地址、MAVLink 消息等可能是高价值技术内容。
- 不以点赞数、回复数、是否已解决作为唯一硬门槛。无人回复的问题可以提供故障事实，但不能自动标成已证实解决方案。

### 存储与向量索引区别处理

- 纯感谢、顶帖、重复引文、系统动作通常不单独生成向量；但“这个参数修改后问题解决了”属于验证信号，需要结合上下文保存。
- 单条回复切片携带主题标题、原问题摘要、必要父回复及原始链接。不能把“改成 2 就好了”作为无上下文的独立技术证据。
- 可另生成问题—诊断—解决方案摘要，但必须可追溯到具体帖子；保留原始证据，不能只存模型摘要。
- `accepted_answer`、维护者身份、复现与验证证据可用于排序，不视为绝对正确保证。区分问题报告、推测建议和已验证结论。
- 记录固件版本、硬件、机型、日期与参数，避免不同版本建议混用。旧内容以版本适用性过滤，而不是按年龄直接删除。
- 图片、飞行日志和附件链接应保留；只有图片或日志的帖子标记为需附件处理，不能把占位文字当作完整技术证据。

先抽样标注约 200–300 个主题及部分关键回复，覆盖技术区、混合区、广告、短回复和未解决问题；评估保留内容的技术相关性、漏掉的有价值主题、噪声回复比例，以及实际 RAG 问答的证据质量，再调整阈值。

## 5. 现有脚本需要改变的关键点

- `discourse_ingest.py` 抓取的是搜索命中的单条 `post`，命中回复时也会保存该回复；问题是没有展开主题，也没有建立主帖与回复关系。
- 搜索仅处理第一页的前 N 条，不保存发现游标。当前关键词轮换容易重复得到同一批旧内容，去重不等于完整增量。
- `cleaned_text` 包含查询词，导致跨关键词命中同一帖子时内容哈希不同。
- 请求无重试；搜索阶段异常发生在逐帖子异常处理之外，可能遗留 `running` 状态并中断后续论坛。
- `ingest()` 汇总状态固定为 `success`，没有正确反映内部部分失败。
- 默认来源包含 `px4` 和同地址的 `dronecode` 别名，来源身份需要统一。

建议先完成主题级完整采集和可恢复增量，再引入多层过滤与检索评估；不要先扩大关键词或提高抓取频率。
