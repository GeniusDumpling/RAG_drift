#### 4. 统计解释

后续报告和前端需要区分以下指标：

- **扫描视频数**：数据库中符合本版范围的视频数量。
- **任务成功数**：包括有图谱、主题不相关、无材料等成功结果。
- **部分完成数与覆盖率**：单列 `partial_success`；区分任务覆盖率和已发布覆盖率。总览汇总已记录覆盖率任务的通过、跳过和待处理切片，旧任务缺少覆盖率时不纳入切片汇总。单视频状态接口同时返回跳过明细和是否保留旧图谱。
- **有效图谱覆盖视频数**：当前有效版本中实际含实体或关系的视频数，建议分别统计。
- **有效关系数**：当前有效版本证据支持的去重关系总量；相同关系由多个视频支持时，关系数不一定增加，但证据数可以增加。
- **页面展示关系数**：受实体搜索、类型、状态、聚焦范围及节点和连接上限影响的子图数量。

例如 `queued: 0, unchanged: 481` 表示本轮扫描未发现需要排队的任务；`unchanged` 同时可能包含成功和未显式重试的失败任务，不代表全部成功。

## 视频知识图谱抽取质量审计（2026-11-02）

当前图谱存在实质性的实体建模和关系语义问题，已经进入有效图谱，不能仅归因于前端布局或展示截断。原文定位机制工作正常，但“引文确实存在”没有保证“引文支持这条关系”。图谱适合保留为候选知识与证据浏览材料；在修复和验收前，不宜直接把全部边作为可靠事实用于自动推理。

本次仅执行只读数据库查询。没有修改 Neo4j/PostgreSQL 数据，没有触发构图、模型调用、迁移、撤回或清理。工作区只新增本报告与样本文件。

### 审计范围与方法

- Neo4j 快照开始时间：2026-11-02 12:38:23，Asia/Shanghai。多条查询依次执行，非跨数据库一致性快照；运行中任务的状态随后可能变化。
- 统计对象与应用接口一致：视频的 `active_build_id` 指向的构图版本，排除已撤回和已删除的视频。没有把历史非活跃证据计入质量统计。
- 读取全部有效实体、别名、提及、关系和证据做确定性检查；读取对应 PostgreSQL 的 **1,442 个源切片**核对原文及字符偏移，全部找到。
- 从去重后的 **2,693 条有效关系**中，将 relation ID 排序，使用 `random.Random(20261102).sample(..., 60)` 抽取 60 条，覆盖 **43 个视频**。每条选择一份有效证据并检查完整源切片；样本中仅 R042 有额外证据，亦已检查。
- 另按 8 种谓词各抽 10 份证据做诊断性检查，随机种子同为 20261102；报告中的 S 编号来自该样本。诊断性案例不计入随机 60 条的质量比例。
- 人工语义评判仅检查保存的字幕是否支持关系，不核实视频说法的现实真实性，也不估计召回率。当前抽取规则的“不合规”也不自动等于现实事实错误。

可复核样本保存在 [`video-graph-quality-audit-2026-11-02.samples.json`](video-graph-quality-audit-2026-11-02.samples.json)，包含随机样本、逐条判断、实体/关系/证据 ID、视频地址、时间、完整源切片，以及单独标识的诊断性案例。数据库全量临时快照保存在 `/tmp/rag_graph_quality_snapshot.json`，源切片在 `/tmp/rag_graph_quality_sources.json`；临时文件不属于长期归档。

### 实体质量与归一化

**泛称被作为全局同一实体。** `drone`（product）聚合了 28 个视频中的 55 次提及，并连接 24 个视频贡献的 65 条关系。上下文分别涉及 Mini 4K、Mavic Mini、Mavic Pro、坠河维修等不同对象。当前稳定 ID 按类型和名称生成，会把这些不同设备的局部描述汇总到同一个节点。类似 `无人机`、`aircraft`、`battery` 等，需要区分“类概念”“型号”“具体设备”和“指代提及”。泛称本身不是天然错误；问题是当前图谱没有表达这些层次及事实适用范围。

**同一型号的名称变体又被拆开。** 数据中 `DJI Neo`、`Neo`、`The Neo` 分别建为 product；第二代又有 `DJI Neo 2`、`Neo 2`、`Neo2`、`DJI Neo2`。这些名称应结合制造商、型号、代际和具体上下文进行候选对齐，不能直接按包含 Neo 一律合并。`DJI fly app` 与 `DJI fly` 也是不同节点。

**跨语言/字形没有系统归一。** `中国` 与 `中國`、`美国` 与 `美國` 等分别存在。当前 4,102 个实体对应 4,104 个别名，其中 **4,101 个实体只有一个别名，只有一个实体有三个别名**。这是本库的实际分布，说明多名称融合在现有数据中的覆盖极低。

**类型不一致。** 除明确地名误标外，`drone` 还被分别标为 product、organization、method；一些故障被保存为整段状态短语；人名、事件、文件、IP 地址在缺少合适类型时被塞入现有类别。136 组跨类型名称中也有合理的多义用法，不能直接批量合并或删除。

### 当前规则与存量数据存在差距

本次 **676 个任务以及 294 个有效构图版本**的记录均为：

```text
video-graph-v1:deepseek-flash
```

当前工作区 `.env` 则配置 `deepseek-v4.1-flash-economy`。因此当前 Neo4j 快照不是使用该新配置重新构建后的效果；版本字段只证明记录的模型标识，不证明上游实际模型权重或在线服务当前配置。

当前源码已经增加地理实体和关系端点语义规则，但默认版本仍是 `video-graph-v1`，源码注释也明确不自动触发历史重建。扫描相同材料和版本时会跳过成功结果。故“源码已有约束”不能作为“全部存量数据已经过该约束”的证据；本次全量复查明确发现未通过当前规则的有效数据。

### 覆盖率与展示的影响

查询时任务状态为：success 270、partial_success 24、failed 250、pending 131、running 1。**任务成功不等于抽取正确；任务失败也不等于视频中的知识不可抽取。**

### 当前候选：实体审核后逐对判关系

```text
当前原文 + 仅用于消歧的标题/邻文
  → 提出实体及属性候选
  → 独立审核实体原文、类型、身份、属性与检索价值
  → 按原文位置与类型兼容性产生有界实体对问题
  → 分批逐对分类：明确回答有关系或无关系
  → 对候选关系另行分批、独立核对原文
  → 程序校验引用、身份、原文位置、类型、方向、条件与否定
  → 一次性归一、去重，生成现有抽取结果及来源校验凭据
```

摘要切片仅执行实体步骤，不产生关系。标题和上下文可以帮助实体消歧，但关系事实必须有当前字幕证据。分类阶段不能增加端点，实体对不是事实；审核调用不接收分类阶段的解释，按原文重新判断。

实体名称保持原语言和完整型号。相同文字可对应不同设备上的部件；先区分身份，再去重。明确型号或概念沿用全局身份，设备部件及未消歧的泛称沿用视频内身份。实体审核不能把数值参数变成独立技术实体；参数作为已有实体的原文属性保存。某项属性无依据时只拒绝该属性。

引文先做空白和排版标点的受限匹配；繁简体回退使用固定版本OpenCC的`t2s`字形转换，仅在长度可保持位置映射且唯一匹配时接受，然后恢复成源文字符。没有增加翻译、同义词模糊匹配或跨型号修补。

### 最小Schema与实现

复用`ChunkExtraction`及现有审核结果。没有新增持久化字段、数据库表、实体类型或谓词。初抽仅输出`entities`；实体对分类和审核复用关系裁决结构，通过`index`关联程序持有的实体对。多种合法关系可以共用一个实体对，明确无关系时返回一条否定裁决。

模型只判断一个关系谓词；原来的重复语义标签`basis`由程序根据审核后的谓词和端点类型派生，供已有来源检查器使用。来源存在不等于关系成立，类型合法也不代表语义成立；独立模型审核仍可能误判。

### 调用量与格式修正

实体识别及审核共2次。关系阶段每16个候选实体对分类一次，每8条候选关系审核一次；每段最多96个候选对、80条候选关系，不含格式修正最多18次阶段请求。每次阶段最多一次结构修正，每次传输最多2次尝试，最坏上限72次HTTP尝试。摘要正常2次；少于2个实体跳过关系。代价高于旧版正常3次流程，是否值得必须结合实测质量判断。

格式修正不用于翻转已经合法的否定裁决。重复、遗漏、非法枚举或无法定位的单项在修正后仍失败时被隔离，有效项继续保留。整个实体审核没有任何可用裁决则作为失败，防止空结果覆盖旧图谱。跨审核批次统一处理去重、所有者拆分和来源凭据索引。

## 实体抽取：口径、领域词表与错误分类

本文保留运行时仍适用的实体口径、领域词表和错误分析说明；旧实验分数与逐轮产物已清理。当前策略、101条标准及两轮结果见[实体评测入口](knowledge-graph-evaluation.md#实体计分)。

### 1. 统一标注口径

[标注规则](../scripts/evaluation_data/entity_gold_guidelines_v3.md)按“提到什么 → 对应哪个对象 → 是否值得入图”定义判断顺序，并列出产品、部件、软件、技术、方法、故障及协议的边界。保留人工已经确认的固件=software、完整遥控器/飞行眼镜=product。

运行时通过同一份`ENTITY_SCOPE_RULES`约束初抽和实体审核，不新增模型阶段。对可整词确定的固件、完整遥控器和眼镜，程序按确认口径纠正类型；遥控器电路板、眼镜屏幕、固件芯片不因名称中包含这些词而被改类。

实体审核可返回已有的`surface_text`字段，收窄候选边界，例如去掉尺寸或普通修饰。修正必须来自原候选内部的连续原文，且不能缩成纯参数；失败时保留原边界并记录原因，不能移到正文中另一对象，也不能增加型号词。

### 2. 小型领域词表

[词表JSON](../backend/app/services/video_graph/terms.json)包含42条项目常见术语，每条只有`name/type/aliases`。包含型号、完整控制器/眼镜、软件及技术概念；它是拼写、类型和候选参考，不是产品规格库，不证明型号已发布或关系成立。

[运行时实现](../backend/app/services/video_graph/terms.py)只向模型提供当前正文匹配到的条目，最多24条；只从正文补充候选，仍须通过独立实体审核和来源校验。新词不受词表限制，不能因为不在表中就丢弃。型号匹配保留代际、Pro/Lite等变体，不从未知型号截取一个旧型号；短型号也不能仅凭词表补造品牌。

词表文件与实现都进入策略指纹，修改后旧抽取缓存不能直接当作新策略结果；JSON已加入Python打包数据配置，没有新增数据库字段、表、实体类型或模型依赖。

词表和口径参考了项目现有内容，包含开发样本出现的术语。当前golden是开发集，不能把这一轮分数当作未见术语或新视频的泛化成绩。

### 3. 独立错误分析

新增[分析脚本](../scripts/analyze_entity_gold.py)，按漏识别、类型、归属、边界/命名、价值筛选、待判读六类解释原有FP/FN。它不修改预测、标准答案或严格评分，不以名称相似给预测补分。

脚本可读取精确请求缓存，区分“候选没提出”和“提出后被审核拒绝”，并核对缓存请求、响应及正文。明确的类型冲突可自动识别；同一部件词涉及多个设备时保守处理，不能看到一个不匹配的所有者就判错。其余项目读完整原文和候选审核记录后由助手分类，未经用户逐条确认。

复用方式：

```bash
.venv/bin/python scripts/analyze_entity_gold.py \
  --evaluation data/video_graph_runs/entity-gold-prompt-edit-repeat-20261105.json \
  --response-cache data/video_graph_runs/entity-prompt-edit-repeat-responses-20261105 \
  --output data/video_graph_runs/entity-gold-prompt-edit-repeat-errors-20261105.json \
  --report docs/entity-gold-prompt-edit-repeat-errors-2026-11-05.md
```

可以修改分析JSON中每项的`category`及`note`再执行，生成统计和阅读版。原始实体、错误项范围、评测指纹及严格计数发生变化时会拒绝沿用旧分析，避免解释文件掩盖实际错误。失败/待运行样本仍保留全部FN，并与语义漏抽区分。

## 实体归一：名称参数、别名与部件所有者

归一层在实体模型审核之后、关系生成之前运行，复用现有实体、属性、身份和原文提及结构，不新增模型调用阶段。本文保留实现与边界说明；旧实验产物已清理，当前策略与评测结果见[实体评测入口](knowledge-graph-evaluation.md#实体计分)。

实现：[video_graph_normalization.py](../backend/app/services/video_graph/normalization.py)。入口调用前后均检查来源与结果凭据；只处理已经通过实体审核的结果，不接受带有关系的输入，避免在关系生成后改名或拆分导致端点失效。

### 1. 分离名称与参数

- 对可完整解析的尺寸、焦距、光圈、像素、数量等修饰，将核心部件名称与参数分开，例如“1/1.1英寸的方形传感器”得到核心名称“方形传感器”，属性保留原文“1/1.1英寸”。
- 对已知具名技术前后的纯视频规格做同样处理，例如“4K 60帧的HDR视频”归为HDR提及，保留`video_resolution=4K`、`frame_rate=60帧`。这是本次提及的修饰信息，不是HDR技术的全局通用规格。
- 原始长提及继续保留，核心短提及必须实际存在于正文。明确的所有者名只添加一次，不把型号重复拼进部件名。
- 不处理无法完整解释的修饰；不从Mini 4K、Cortex M7等名称里拆型号数字，不把多个配置强行合成一个值。属性冲突不覆盖已审核值，仍受现有属性数上限约束，原文一直保留。

### 2. 合并同一对象的不同叫法

- 当前正文只对应一个明确设备，或固件规范名已明确该设备时，`firmware`与`drone firmware`可以指向同一视频内固件身份；各自原文提及保留。设备不唯一或规范名明确区分版本时保留区别。
- 同一具名设备与已经明确解析到它的局部回指，可在有明确依据时统一作用域。正文出现多个实际设备时不自动提升泛称身份。
- 添加所有者时保留已审核的名称归一结果，例如完整缩写解释与短缩写已指向同一板件，不再按长原文重新扩出第二个身份。
- 多个提及仍可对应一个实体UUID，便于保留各条来源。关系候选按归一身份去重，避免别名重复提问；同一身份之间的自关系也会被拒绝。

### 3. 区分不同设备的同名部件

- 使用已审核设备作为所有者锚点，匹配正文中明确的所属、列举或“各自具有”表达。例如“A、B的广角镜头”可分别保留两个设备的镜头，均保持视频内身份及原文依据。
- 同一个部件词多次出现时，结合已经审核的规范名及明确原文定位；单次提及且所属表达唯一时，可以按原文纠正错误所有者。
- 原文明示共用的硬件不拆成多个实例；比较、同段共现和空间距离本身不构成所有权依据。无法确定时保留原审核身份。
- 拆分不自动创造contains或其他事实关系，也不把未分别归属的属性、配置或动作复制给所有设备。每个拆出的身份均须通过来源检查；不完整通过则保留原结果。
- 对只有大小写差异、且多次匹配的源文字符完全一致的提及，可以恢复源文写法；多个大小写形式不同的匹配仍判为歧义。受控中文品牌转英文时保留词边界，避免把品牌与型号粘成一个词而拒绝正确归属。

#### 四个环节的约束

1. **事实先核验**：实体原文必须能定位；类型、规范身份、所有者和属性仍需证据。数值参数不能以“延后筛选”为由变成实体。属性拒绝不会自动删除有依据的实体。
2. **价值后判断**：初抽和事实审核不再仅因泛称、无型号或价值暂不明确就淘汰部件、配套设备及维修对象。最终价值判断同时读取原文、实体和已审核关系；有独立信息的孤立实体也可以保留。
3. **关系参与最终保留**：有事实关系不等于必须入图。最终裁决只提供保留掩码，不能改写已核验的类型、身份、属性、谓词、方向、断言或条件。删除实体时同步删除关联边；关系证据保持一一对应并重编号。
4. **补漏只执行一轮**：最多8个有原文的新端点，受每段60个实体总容量限制。补充不能覆盖既有key或身份，也不能凭常识创建缺失型号。新实体须独立审核，关系也须独立审核；没有最终保留关系的新端点不会作为孤立节点发布。没有事实锚点的空实体池不执行补漏。

实体对继续受类型、原文位置及96对预算限制；补漏的“涉及新端点”过滤在预算截断之前执行。分类每批16对、事实关系审核每批8条，最终最多80条关系。开箱语境新增显式开箱/打开包装表达，同时保留主体切换及实际安装的区别校验。独立审核未返回条件字段时保留原有合法范围，显式非法范围仍拒绝；类型唯一的反向关系在独立审核前及审核后校正。

### 规范与实现

| 场景 | 统一表达 | 边界 |
|---|---|---|
| 外部App、编辑/导入软件、操作方法应用于设备 | 软件/方法 → applied_to → 设备 | 须有原文工作流依据；不从仅共现推导 |
| 设备内置固件、运行软件、所用技术/数据 | 设备 → uses → 资源 | 不把所有uses都反转为applied_to |
| 整体与自身部件 | 整体 → contains → 部件 | 物主词、拆换对象、连续指代可说明归属；跨设备比较不能强绑 |
| 部件安装 | 部件 → installed_on → 载体 | 安装不自动等价于物理包含 |
| 产品品牌归属 | 产品/系列 → offered_by → 组织 | 正文品牌+型号可作依据；规范名自行补出的品牌不作新事实 |
| 产品系列与型号 | 系列 → has_model → 型号 | 比较或替代不自动产生型号归属 |
| 兼容、连接 | compatible_with / connected_to | 沿用语义对称口径；不将连接软件误写为USB硬件连接 |

1. 在共享语义规则中区分外部工作流与内置运行，分类和独立审核使用同一口径。新增`canonicalize_relation_expression`，仅对有逐字原文及外部工作流证据的软件/方法关系规范谓词和方向；分类后、审核后均执行。保留引文、assertion、qualifiers和端点身份。已有类型唯一的方向纠正规则继续使用。

2. 每个候选对按实体类型增加简短question，明确要核对的角色：品牌归属、系列代际、整机部件、部件控制/接线、实际配用等。question是问题而非事实；模型返回false时不创建关系。实体初抽、价值筛选、归一策略和96对预算不变，没有重新引入实体补漏或放宽实体池。

3. 审核输入显式提供quote_valid。无效引文的批次附原文source_lines，允许返回连续行号quote_lines；程序复制原文，检查行号、顺序、6000字符上限及原有来源/语义约束。没有使用同义词匹配、删词或模糊引文补救。

4. 支持项没有按要求修复无效引文时，进入原有最多一次格式修正，不将该不完整肯定裁决冻结；其他合法肯定/否定裁决仍冻结。修正后仍缺失则隔离，不循环重试，也不绕过原文校验。

实现：[共享语义与规范化](../backend/app/services/video_graph/semantics.py)、[分类/审核与证据修复](../backend/app/services/video_graph/review.py)、[新增29项契约测试](../backend/tests/test_video_graph_relation_expression.py)。

## 视频图谱 token 开销优化

2026-11-10更新：当前模块已归入 `app/services/video_graph/`，在线图谱仅使用 Neo4j；以下保留原实现/评测记录，当前职责及兼容边界见[模块重构说明](knowledge-graph-history.md#video-graph-refactor-2026-11-10)。

### 采用的实现

本次按“实际用量统计 → 输入输出精简 → 批次试验 → 重试复用”的顺序进行了评测。最终保留**阶段用量统计和任务内持久化请求检查点**。提示词、模型参数、请求 JSON 格式、分类批次16、独立审核批次8全部恢复为优化前状态。

精简和扩大批次虽然降低了请求 token 数，但在固定实体的关系对照中未稳定保持质量，因此没有作为默认实现。不要把实验文件名中的 `final` 理解为采用版本；最终采用版本的评测文件是 `token-accepted-20261106.json`。

#### 用量统计

`LLMVideoExtractor.token_usage.snapshot()` 按主题判断、实体抽取、实体审核、关系分类、关系审核统计：

- `http_attempts`：实际 HTTP 尝试，包括失败请求。
- `prompt_tokens`、`completion_tokens`、`total_tokens`：服务商返回的真实用量；模型输出无法解析但已有 usage 时也计入。
- `cached_tokens`、`uncached_prompt_tokens`：仅在服务商返回合法缓存用量时记录。
- `reasoning_tokens`：仅在服务商返回时记录。
- `measured_responses`、`unknown_usage_responses`：区分已知和未知用量；缺少 usage 不当作免费。
- `checkpoint_replays`：本地持久化检查点复用次数，不当作服务商缓存命中。

`pipeline` 报告增加 `token_usage`（本次命令）和 `cumulative_token_usage`（同一清单已保存报告的累计值）。无调用的幂等重跑不会增加累计值。`usage_history_complete` 表示既有报告是否连续包含统计；不保证捕获进程突然终止前未落盘的用量。日志不输出密钥、服务地址或原文。

这些字段不是人民币账单。输入缓存、普通输入和输出的单价不同；本次没有假定价格，也没有用字符数代替 token 数。

#### 持久化请求检查点

以前只有完整切片的检查点。一个片段最后一步调用失败，重新领取任务后仍需重新运行此前的抽取与审核。

现在 PostgreSQL 和 Neo4j worker 都在成功请求返回后，将可解析的 JSON 对象响应保存到本构建的 `output_json.request_checkpoints`，然后才继续下一次模型调用。重试或租约到期换 worker 后，完全相同的请求可以直接恢复。

复用键绑定抽取版本、模型及所有请求参数、完整 system/user 消息、服务商/账户哈希、当前任务和切片范围。数据库仍使用原有租约和目标构建检查。新切片、上下文或规则产生不同请求，不能误用旧响应；不跨视频共享候选。

响应保存为 JSON 字符串并带内容哈希。这样 PostgreSQL JSONB 调整对象键顺序后，也不会改变恢复时下游请求的 JSON 字符串。损坏的条目重新调用；调用异常不缓存。结构或来源校验异常会清理对应片段的请求检查点；正常的实体/关系审核拒绝仍按原逻辑处理。片段完整通过审核后，删除该片段的原始响应缓存，只保留正常结果和审核凭据。

**复用成功响应后，实体规范化、独立关系审核、原文定位和最终入库验收仍执行。** 这不是跳过审核或给无效结果补证明。

模拟最后一条证据修正请求连续两次 HTTP 500 后换 worker，两个后端均验证：重试所需模型请求由5次减少为1次，另外4次从数据库检查点恢复，最后成功入库并检索到原文。这里的80%是该失败恢复场景的调用数降幅，不是所有视频的平均 token 降幅。首次全部成功的任务调用量保持原样。

| `identity.py`、`normalization.py`、`semantics.py`、`grounding.py`、`terms.py` | 身份归一、类型/方向/断言约束、证据校验及术语表 |
| `tasks.py` | 唯一的来源扫描、任务领取后执行、切片恢复、失败处理和发布编排 |
| `storage.py` | 唯一的图谱/任务存储：Neo4j 视频锁、排队、领取、续租、检查点、事务发布、撤回、有效状态快照 |
| `queries.py`、`evidence.py` | 有效投影查询、图谱遍历、原文证据、时间定位、检索上下文 |
| `backfill.py`、`pipeline.py` | 固定范围计划、有界执行、完整发布与查询验证闭环 |
| `request_checkpoint.py`、`usage.py`、`diagnostics.py` | 阶段响应检查点、真实 token 统计、脱敏错误诊断 |

旧的 `services/video_graph.py`、`services/video_graph_*.py` 及 `services/neo4j_graph/` 已删除，不保留导入转发层。`__init__.py` 只描述包职责；调用方直接从相应职责模块导入。

`build_graph.py` 仍为命令行入口；图谱 API 的 `/video-graph/*` 路径和数据结构保持兼容。`graph_retrieval.py` 保留为问答与图谱 API 共用入口，只连接 Neo4j；`answer_graph.py` 继续回业务切片验证来源与过滤条件。

调用链为：

```text
CLI / pipeline / backfill
  → tasks.enqueue_videos / process_next
  → storage.claim / checkpoint
  → extraction → review → validation
  → storage.activate（源指纹、目标构建、租约校验与事务发布）
  → queries（图谱、提及、证据与检索验证）
```

原来 PostgreSQL 与 Neo4j 各有一份 worker、发布和查询实现，现在只剩一条 Neo4j 流程。计划和验证共用 `GraphStore.active_snapshot()`，不再分别维护 SQL/Neo4j 状态判断。阶段响应复用、切片恢复和 token 统计仍使用同一套实现。

### PostgreSQL 与 v1 的保留边界

重构前只读盘点发现：

- PostgreSQL 留有483个 v1 构建（213成功、20部分完成、250失败）、2,130条关系、2,215条证据。
- Neo4j 有294个有效视频构建，均为 `video-graph-v1:deepseek-flash`；还有历史失败/待处理/运行中任务。

因此没有删除历史数据或直接丢弃 v1 读取能力。

| 项目 | 处理 |
|---|---|
| 在线 PostgreSQL 图谱入库、排队、领取、发布、查询 | 删除 |
| `VIDEO_GRAPH_BACKEND` 配置及 API/CLI/问答后端分支 | 删除；环境模板和 Compose 不再设置该字段 |

旧 v1 任务不能直接交给新 worker 继续生成；如需升级某视频，使用当前 v2 版本新建有界计划。已有旧版本计划会因目标版本不同被拒绝。实际部署更新前应协调已有旧 worker，避免继续执行旧代码；本次未代替运维做停机或重建。
